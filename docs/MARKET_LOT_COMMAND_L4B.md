# L4b — закрытая команда резерва партий

## Приёмка
1. Проверяется сессия, организация, объект и stock.manage; права повторно проверяются после блокировок.
2. Все текущие позиции заказа получают ровно одну выбранную партию; количество берётся из БД.
3. Один ключ с тем же телом возвращает прежний результат; другое тело с тем же ключом даёт конфликт.
4. Резерв/освобождение, ревизия, команда, аудит и outbox атомарны; откат не оставляет частичной операции.
5. Освобождение допустимо после окончания проживания; новый резерв требует действующего заезда.
6. Цена, общий SKU-резерв и физический остаток не изменяются; пользовательская активация отключена.

Migration0118: service_private.market_lot_command(session_hash,order_id,key,body).
reserve_lots: expectedRevision и selections [{itemId,movementId,lotCode,expiresOn}] для всех строк.
release_lots: expectedRevision и note (3–500 символов); освобождаются все активные привязки.
Тело строгое; порядок selections входит в сравнение payload. Нормализация HTTP-клиента — будущий слой.
Повтор возвращает историческую квитанцию и не восстанавливает уже освобождённый резерв.
Внутренние LOT_RESERVE_* ошибки сохраняются до добавления согласованного API-контракта.

Блокировки: ключ команды → проживание → заказ → товары в порядке UUID.
Проверки сессии/прав повторяются после ожидания ключа и бизнес-блокировок.
Существующие helpers записывают service_private.commands, audit_log и outbox_events;
квитанция содержит выбранные партии, а освобождение — причину.
Функция private, EXECUTE для PUBLIC отозван; wrapper app/API/UI отсутствует.

Ручная приёмка: обычные операции маркета должны работать без новых привязок;
пользовательский DB-клиент не должен вызывать private-команду. Для проверки записи использовать только
одноразовый runner с синтетическими сессиями, не рабочую БД.

Ограничения: это внутренний код, не пользовательский режим. Дальше атомарное освобождение при отмене,
замене и выдаче; затем API/UI и проверка всех путей до включения. FEFO/публичный веб/APK не менялись.
