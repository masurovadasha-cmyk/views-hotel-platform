# Заказ уборки — серверный блок Core

Состояние этого серверного блока: локальный тестовый пилот. Последующее
подключение локальных UI/BFF описано в [SERVICE_CLEANING_WEB.md](SERVICE_CLEANING_WEB.md).
Опубликованные веб/APK процесс пока не используют. Расширение существующих реестров, без нового движка
оплаты и без подключения партнёров. Цена из каталога считается итоговой;
налоги отдельно этот блок не рассчитывает. Значения цены/длительности в тестах
синтетические, не коммерческое предложение и не обещание SLA.

## Схема и процесс

Миграции 0068–0070: опциональные метаданные исполнения/версия каталога,
`service_cleaning_tasks`, приватные идемпотентные команды и функции Core.
Существующие записи каталога не включаются автоматически. RLS ограничивает
чтение объектом/организацией; прямых политик изменения задач нет.

`requested → assigned → working → inspection → done`.
Инспектор может вернуть `inspection → rework → working`; до начала работы
диспетчер может отменить заявку. Гость должен быть заселён и владеть бронью
через привязанный профиль. В заказе фиксируются название, цена bigint,
комиссия, длительность, юнит и чек-лист. Изменение цены до заявки требует
повторного согласия; после заявки не меняет стоимость заказа.

Назначает сотрудник с `reservation.manage` на горничную с действующим доступом
к объекту. Работает только назначенный сотрудник с `housekeeping.work`.
Принимает другой пользователь с `reservation.manage` — вторая роль того же
человека не позволяет проверить собственную работу. Приёмка, запись в фолио,
закрытие заказа, аудит и outbox происходят в одной транзакции. Закрытое фолио
отклоняет приёмку без частичных записей. Начисление не является оплатой.

EXCLUDE запрещает пересечение плановых интервалов активных назначений одного
membership. Это пока планирование по выбранному времени, не учёт фактической
смены/переработки: ранний старт не блокируется; несколько memberships одного
работника не объединяются в общий календарь. До UI-пилота нужны подтверждение
времени гостем, единый календарь человека и политика просроченных заданий.

## API

Все ответы `Cache-Control: no-store`, списки по 50 строк с `nextCursor`.
Гостевой Bearer — существующая Core email-сессия; сотруднику нужны существующие
Core actor headers и `x-views-staff-session`. Дополнительные требования шлюза
и защитные проверки приложения сохраняются. Заголовки ролей не заменяют сессию.

| Метод | Путь после `/v1/` | Данные |
|---|---|---|
| GET | `guest-identity/email/services/catalog` | `reservationId`, необязательный `cursor` |
| GET | `guest-identity/email/services/orders` | те же параметры |
| POST | `guest-identity/email/services/orders` | тело ниже, `Idempotency-Key` UUID |
| GET | `service-orders` | `propertyId`, необязательный `cursor` |
| POST | `service-orders/:id/actions` | действие, `Idempotency-Key` UUID |

Создание: `{reservationId, serviceId, expectedRevision, expectedPriceMinor,
requestedFor}`. Цена — положительная десятичная строка; время — ISO UTC
`2026-10-15T10:00:00.000Z` в пределах проживания с учётом длительности.

Действия: `{action, expectedRevision, ...}`; `assign` требует `assigneeId`,
`start` без дополнительных полей, `submit` — `note` и
`checklist: {linen:true,bathroom:true,floor:true}`. `approve`, `reject`, `cancel`
требуют `note`. Неожиданные поля запрещены. Повтор команды с тем же ключом и
телом возвращает исходную квитанцию; изменённое тело — конфликт. Новая команда
использует новый ключ и актуальную ревизию. После таймаута повторяют исходный
ключ, а не создают новую финансовую операцию.

## Запуск и проверки

Из корня, при установленных зависимостях и Docker:

```sh
npm --prefix apps/api run typecheck
npm --prefix apps/api run build
node scripts/cloud-core-tests.cjs
```

Последняя команда сама поднимает одноразовую PostgreSQL 16, применяет миграции,
тестовые сиды и выполняет полный набор Core; удаляет только свой контейнер.
`service-orders.synthetic.sql` отказывается работать без маркера одноразовой
БД. Нельзя направлять этот сид на `views_local` или production.

HTTP-пилот требует одновременно `NODE_ENV=test`, `VIEWS_LOCAL_REHEARSAL=true`,
`VIEWS_SERVICE_ORDER_PILOT_ENABLED=true`, а также существующую настройку гостевой
и кадровой авторизации. Не включать эти флаги на публичном сервере. Для SQL
используется существующий ограниченный runtime-role; функции `service_private`
ему недоступны. Публичный каталог нуждается в отдельно утверждённых данных.

## Что проверить перед следующим блоком

- [ ] Подключить BFF и экраны гостя/диспетчера/горничной по PDF, затем HTTP/browser-тесты.
- [ ] Проверить выбранное время, отсутствие гостя, DND, смены, задержки и переназначение.
- [ ] Согласовать реальные цены, состав уборки и длительность по объектам.
- [ ] Добавить отмену гостем, спор и контролируемое сторно начисления.
- [ ] Добавить фото с контролем доступа, доставку уведомлений и SLA-таймеры.
- [ ] Проверить отделение платной уборки гостя от обязательной уборки после выезда.

Пока нет фото, доставки уведомлений, платежей, возвратов, автоматического
выпуска номера в продажу и интеграции с прежней очередью housekeeping.
Финансовая запись этого блока не поддерживает старое ручное сторно фолио.
Внешних расходов, миграции постоянной БД и публикации нового APK не требуется.
