# ADR 0004 — единая модель и границы организаций

Дата: 8 октября 2026, Ташкент. Этап Б0.
Статус: сохраняем существующую модель; расширения проходят новые миграции и тесты.
Дополняет ADR 0002 о непривилегированной роли БД.

## Решение

Одна схема PostgreSQL, организация типа `platform` для собственного фонда и
`host` для стороннего хозяина. Цепочка: организация → объект → тип юнита → юнит;
тариф принадлежит объекту/типу, бронирование фиксирует юнит и тариф. Для 500 апартаментов четырёх городов требуется пагинация и массовый импорт;
город — поле объекта, а не самостоятельный tenant. Публичный
каталог — безопасная проекция разрешённых к публикации данных, не обход RLS.

- Сервер получает actor из проверенной сессии/подписи, разрешает membership,
  role/permissions и property scope. Organization ID из формы не даёт доступа.
- RBAC и RLS применяются вместе. API использует views_app без SUPERUSER/BYPASSRLS;
  миграции — отдельную учётную запись. Контекст tenant задаётся через SET LOCAL
  внутри транзакции, чтобы пул соединений не переносил его следующему запросу.
- Таблицы Б1 получают organization_id и индексы доступа; у зависимых таблиц без
  собственного tenant — проверяемая связь с родителем и RLS через него.
  Новые связи предотвращают cross-tenant reference составным FK либо проверяемой
  политикой. Старые отношения сначала анализируются, затем исправляются совместимо.
- Гость получает доступ к своим броням/поездкам, а не роль сотрудника организации.
  Публичный поиск раскрывает только опубликованные поля/наличие, без PII гостей.
- Хост видит только свои организации/объекты; сотрудники — назначенный scope.
  Владелец/менеджер/бухгалтер получают явные разрешения, не выводимые из UI.
- Админ платформы использует отдельные административные операции, MFA и аудит
  причины доступа. Роль админа приложения не делает его PostgreSQL superuser.
- Маркетплейс разделяет владельца бронирования, продавца услуги, комиссию и
  обязательство перед хостом. Перевод между организациями — явная операция с
  полномочиями на обе стороны, а не временное отключение RLS.
- Версии защищают от потери изменений; идемпотентность привязана к организации,
  типу операции, actor при необходимости и хешу команды. Аудит/outbox атомарны.
- Единая inventory_periods и EXCLUDE по юниту/полуоткрытому интервалу остаются
  последней защитой от двойной брони. Redis или UI её не заменяют.

## Альтернативы и последствия

База на каждого хоста слишком усложняет агрегированный поиск, миграции и учёт.
Общая схема требует отрицательных тестов каждой новой таблицы/операции. Разделение
по региональным кластерам возможно позже через tenant/region routing; запросы
между регионами используют договорённые проекции, не произвольный общий SQL.

## Проверка решения

Для каждой таблицы Б1: RLS SELECT/INSERT/UPDATE/DELETE, чужой родитель, отозванное
членство, ограниченный объект, повторное использование pooled connection.
Для денег/доступности: гонки, rollback и разрешённый повтор. Реальные учётные записи
не повышаются в правах ради тестов; расширения проверяются в одноразовой БД.
