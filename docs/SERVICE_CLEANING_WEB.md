# Уборка: гостевой интерфейс и рабочие места

Продолжение серверного блока `ddabde2`. PostgreSQL Core остаётся источником
заказов и финансовых записей. Доступ только в локальном пилоте, не в публичном
демонстрационном каталоге. Новой модели платежей или платных ресурсов нет.

## Что добавлено

- В деталях заселённой поездки: каталог уборки с ценой, выбор времени по часовому
  поясу устройства, согласие на начисление в фолио, список и страницы заказов.
- В кабинете сотрудника с `reservation.manage`: очередь настроенного объекта,
  выбор горничной, отмена до начала, возврат на доработку и отдельное подтверждение
  инспекции/начисления. Сервер запрещает принимать собственную работу.
- В кабинете горничной: собственные назначения, начало, три пункта чек-листа,
  комментарий и сдача на проверку. Это отдельная очередь платных услуг, не замена
  существующей уборки после выезда.
- RU/UZ/EN и существующие темы. Нет сети — действия заблокированы. При неизвестном
  результате повторяется исходное тело с исходным UUID; новые действия блокируются.
  Пока результат неизвестен, браузер предупреждает перед уходом со страницы.
- BFF хранит авторизацию в существующих HttpOnly cookies; проверяет origin/CSRF,
  запрещает подмену actor и не отдаёт гостю служебные поля.

## Миграция

`0071_cleaning_assignees.sql` добавляет только функцию чтения горничных объекта.
Она проверяет действующую кадровую сессию и `reservation.manage`, ограничивает
организацию/объект, активность пользователя и назначенную роль. 501-я строка
служит признаком ограничения списка 500 сотрудниками. Сиды 0068–0070 не меняются.
`0072_cleaning_queue_unit_labels.sql` добавляет читаемый код юнита в ответ очереди
без переписывания предыдущих миграций.
`GET /v1/service-orders/assignees?propertyId=UUID` используется через BFF.
В этой версии BFF использует объект существующей локальной конфигурации.
Очередь сотрудника загружается только после кнопки «Открыть очередь уборки».

## Повторить доказательство на одноразовом стенде

Из корня репозитория, с установленными зависимостями, Docker и Chromium:

```sh
npm run build
npm --prefix apps/api run typecheck
npm --prefix apps/api run build
VIEWS_GUEST_EMAIL_HTTP_PROOF=true VIEWS_GUEST_EMAIL_BROWSER_PROOF=true node scripts/cloud-core-tests.cjs
npm test
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
```

Нужен свободный loopback-порт 4173. Если он занят, не останавливайте чужой
процесс: используйте отдельную среду. Раннер запускает одноразовую БД и локальный
почтовый приёмник; внешних писем нет. Постоянная `views_local` не используется.
Раннер сам включает `VIEWS_SERVICE_ORDER_PILOT_ENABLED=true` для API и BFF
вместе с существующими локальными флагами идентификации. Для ручной установки
применять миграции штатным операторским процессом с проверкой журнала миграций;
не запускать синтетические сиды на постоянной БД.

## Ручная приёмка и оставшиеся ограничения

- [ ] Проверить цену и названия реальных услуг, длительность и право начислять их в фолио.
- [ ] Пройти гость → диспетчер → горничная → другой инспектор в обеих темах.
- [ ] Отключить сеть после отправки, восстановить и повторить ту же команду.
- [ ] Проверить отмену до старта и возврат на доработку.
- [ ] Проверить фактическую смену, DND, согласование времени и переносы.

Гостевая форма сейчас доступна только в заселённой поездке; отдельный экран
истории услуг после выезда ещё не сделан.
Нет доставки уведомлений, фото, SLA-таймеров, пользовательского сторно,
возвратов или онлайн-оплаты. Выбранное время — плановое, ранний старт сервер пока
не запрещает. Плановый календарь привязан к membership, не объединяет несколько
ролей одного человека. Неизвестная команда живёт в памяти открытой страницы:
если принудительно закрыть её несмотря на предупреждение, нужно сначала
проверить список заказов/фолио. Автоматического повторения после перезапуска нет.

Публичные Cloudflare/Pages/APK остаются 0.13.0-preview: этот процесс требует
локального Core и не включён в опубликованный демонстрационный интерфейс.
