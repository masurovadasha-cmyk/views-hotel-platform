# Б2 / гостевой интерфейс email — локальный проверочный блок

Экран гостя подключён к API миграции0058 через отдельный cookie-шлюз.
Есть запрос письма, явное подтверждение одноразовой ссылки, восстановление
сессии после перезагрузки и выход с отзывом сессии в PostgreSQL. RU/UZ/EN,
тёмная тема, мобильная ширина390 и состояние без сети проверены в Chromium.
Это локальный стенд: реальные письма и публичный вход не включены.

## Схема и границы

Новая миграция не нужна: используются private challenges/sessions из0058;
применённые миграции не менялись. Постоянная БД `views_local` не затронута.

```mermaid
sequenceDiagram
 participant B as Браузер
 participant W as Локальный cookie-шлюз
 participant C as PostgreSQL Core
 participant M as Loopback SMTP
 B->>W: POST /guest-api/request (email, locale)
 W->>C: POST /v1/guest-identity/email/request
 C->>M: Одноразовая ссылка (только тестовый адаптер)
 B->>B: Удалить fragment; ожидать нажатия «Подтвердить»
 B->>W: POST /guest-api/exchange
 W->>C: Обмен ссылки
 C-->>W: Гостевая сессия
 W-->>B: HttpOnly cookie; JSON без bearer
 B->>W: GET /guest-api/session
 W->>C: Проверить сессию
 C-->>B: Гостевой профиль через шлюз
```

- `src/features/guest-auth/` — экран, переводы, стили, разбор fragment до React
  StrictMode; старые приглашения сотрудников сохраняются.
- `src/api/guest-email.ts` — типизированные запросы, таймаут, без авто-повторов.
- `apps/api/ops/guest-email-gateway.cjs` — только четыре разрешённых маршрута,
  фиксированный IPv4 loopback upstream; нет общего прокси и CRM API.
- `views_guest_email`: HttpOnly, SameSite=Strict, Path=/guest-api, max-age7дней.
  Bearer не возвращается в JSON и не сохраняется в web storage. На локальном
  HTTP cookie без Secure; этот шлюз не предназначен для публичной установки.
- Проверяются Host, Origin, Sec-Fetch-Site, собственный заголовок, размер тела,
  запрещённые actor/Authorization-заголовки. Выход требует session-bound HMAC CSRF.
  Ошибки Core фильтруются; redirects запрещены; таймаут10с; максимум12 запросов.
- При недоступности Core существующая cookie не удаляется. Неопределённый ответ
  не повторяется автоматически. Можно явно проверить сессию и повторить выход;
  потерянный ответ обмена без полученной cookie может потребовать новой ссылки.
- Гостевая сессия не выдаёт членство сотрудника и пока не открывает бронирования.
  После входа показывается реальный профиль, без демонстрационных броней.

## Запуск и проверка

Нужны зависимости из обоих lockfile, Node22+, Docker и Chromium. В текущей
облачной среде они установлены. При подготовке новой машины:

```sh
npm ci
npm --prefix apps/api ci
# Если системного /usr/bin/chromium нет:
npx playwright install chromium
npm run cloud:test:guest-email
```

Команда собирает веб/Core, создаёт одноразовый PostgreSQL16, применяет все
миграции/синтетические fixtures, запускает весь набор Core и реальную цепочку
SMTP → браузер → cookie-шлюз → Core → PostgreSQL. По завершении закрывает
свои серверы и удаляет только свой контейнер. Не запускает постоянный кабинет.
Ссылка и cookie остаются в памяти теста; тестовые письма идут только в loopback
SMTP на адреса `@views.invalid`, без доставки во внешний почтовый ящик.

Внутри этого изолированного стенда обычная сборка открывает `api=guest-core`
только на HTTP127.0.0.1 с портом. Сам шлюз дополнительно требует NODE_ENV=test,
VIEWS_LOCAL_REHEARSAL=true, VIEWS_GUEST_EMAIL_PILOT_ENABLED=true, отдельный
случайный CSRF-ключ и отдельный HMAC-ключ Core. Runner задаёт их в памяти.
Обычный `cloud:start`, публичная сборка review и APK этот режим не включают.
Worker отвечает503 на `/guest-api`, не подменяет API страницей HTML.
Не переносите test-флаги и этот HTTP-шлюз в публичное размещение.

Дополнительные проверки:

```sh
npm test
npm run typecheck
npm --prefix apps/api run typecheck
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
npm run build:review
node scripts/access-portal.browser.cjs
```

В GitHub workflow `production-core.yml` добавлены сборка фронтенда и этот
сквозной браузерный сценарий рядом с существующим HTTP/SMTP proof.

## Доказательства

Изменённое дерево на базе1e09005: Core417/74 + SQL-проверки, root261/44,
web/Core typecheck и сборки, network150, mail15 — exit0. Браузер: четыре группы
(вход/перезагрузка/cookie; ограничения шлюза; три языка/мобильный экран/тёмная
тема/потеря сети и ответа выхода; повторная/повреждённая ссылка). HTTP proof:
три группы, два письма в loopback SMTP. Проверены настоящие запросы и БД;
потеря ответа выхода отдельно воспроизведена транспортной ошибкой Playwright.

Первый сквозной прогон выявил ошибку счётчика теста: намеренно отклонённый
обмен409 тоже считался. Проверка исправлена на прирост относительно количества
до повторного открытия ссылки. Повторный прогон прошёл; проверки не отключались.
Логи текущей среды: `/tmp/views-guest-ui-{core,root,review}.log`.
Последняя редакционная правка текста профиля проверяется CI на коммите блока.

## Риски и ручная приёмка

- Реальный почтовый провайдер и публичный HTTPS-шлюз остаются неподключёнными.
  SMTP capture не доказывает владение настоящей почтой. Нет новых расходов,
  платежей, изменения ролей или публичного туннеля.
- Перед публичным подключением нужны Secure cookie, production auth policy,
  проверка доставки/домена, реального клиента почты, rate limits за доверенным
  прокси и согласованное хранение данных. Этот локальный шлюз их не заменяет.
- Проверить вручную чтение и порядок фокуса со скринридером, тексты у носителей
  RU/UZ/EN, переход из реального почтового клиента, очистку/блокировку cookie,
  закрытие браузера, несколько вкладок и истечение7-дневной сессии.
- Реальные мобильные устройства и APK в этом блоке не проверялись/не обновлялись.
  Для публичного входа недостаточно сменить query parameter или флаг сборки.
- Следующее программное продолжение: привязать гостевую идентичность к собственным
  бронированиям с проверками участника и изоляции. Общий этап Б6 не завершён.
