# Б1 — реестры единого Core

Дата: 8 октября 2026, Asia/Tashkent. Базис: `5fc4555`, проверка на изменённых исходниках; тарифный WIP Б2 сохранён отдельно.

## Анализ и совместимое расширение

До изменений журнал `views_local_migrations` содержал 49 миграций. Применённые файлы не изменены. В 0007 уже есть тарифы, ограничения, налоговые правила, снимки расчёта и отмены; в 0008 — платежи и двойная запись; в 0009 — документы, E-mehmon, фискализация и политики размещения данных; в 0019 — экономика брони. Дублировать эти модели нельзя.

Добавлены четыре миграции в `apps/api/db/migrations`:

| Миграция | Модель и ограничения |
| --- | --- |
| 0050 | `guest_folios`, `folio_entries`, составные ключи организаций/объектов/валюты; начисления неизменяемы, исправляются точной однократной сторнирующей записью; записи сериализуются с закрытием фолио |
| 0051 | `service_catalog`, `service_orders`, `promotion_codes`, `promotion_redemptions`, `loyalty_tiers`, `loyalty_stay_credits`; услуги с бронью или отдельно, денежные снимки, лимиты промокодов под блокировкой строки, уникальный зачёт завершённой поездки |
| 0052 | `host_payout_drafts`, `reservation_disputes`, `dispute_events`, `stay_reviews`; черновик выплаты привязан к окончательному экономическому снимку, отзывы по одному от каждой стороны, окно 14 дней и слепая публикация |
| 0053 | Закрытое фолио нельзя открыть или переназначить; цена и получатель заказа услуги неизменяемы, переходы статусов ограничены |

Фолио — расчёты с гостем, не замена бухгалтерской книге. Положительные строки — начисление/возврат гостю, отрицательные — оплата/внесённый депозит. Налоговые строки содержат снимок основания. Связь с журналом двойной записи предусмотрена; автоматическое проведение и сверка относятся к Б3/Б4.

Все новые таблицы имеют FORCE RLS. Новый `app.registry_access` сверяет организацию, пользователя, членство, активность, существующее право и объект. Существующие роли не расширены. Фолио/услуги доступны по правам бронирования, каталоги — управления объектом; финансовые записи изменяет существующая роль с `finance.manage` в разрешённом объекте. Уровни лояльности и промокоды управляются на уровне организации владельцем/менеджером. Гостевой прямой доступ в БД не открыт.

Индексы покрывают очереди по объекту/статусу/времени, выписки фолио, заказы брони, подсчёт промокодов и поездок гостя, очередь публикации отзывов. Составные внешние ключи новых реестров запрещают связь с чужой организацией, объектом или валютой. Индексы существующего EXCLUDE и налогов сохраняются.

## Запуск и проверка

Из корня репозитория:

```sh
npm run cloud:test:core
npm run typecheck
npm test
npm run build
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
```

Из `apps/api`: `npm run typecheck && npm run build`.

`cloud:test:core` создаёт свою одноразовую PostgreSQL 16, применяет всю цепочку, создаёт синтетические данные, выполняет SQL-проверки ограничений и весь Core Vitest. Сид `apps/api/db/seeds/stage-b1.synthetic.sql` требует БД `views` с маркером `VIEWS_DISPOSABLE_CORE_TEST`; против `views_local` он откажется работать. Он создаёт отдельного тестового бухгалтера без пароля/сессии, выключенные тестовые услугу, промокод и уровень лояльности. Данные реальных 500 апартаментов не выдуманы.

SQL-проверки `apps/api/db/tests/stage-b1.constraints.sql` выполняются с откатом. Они проверяют семь групп: выезд, скрытие до ответного отзыва, уникальность, публикацию двух сторон, неизменяемость, срок написания, основание выплаты. Семь интеграционных тестов под ограниченной ролью проверяют bigint, сторно, закрытие, валюту/RLS/подмену пользователя, финансовые права, параллельный промокод, лояльность и заказ услуги. CI использует те же файлы.

## Ограничения и ручная приёмка

- Б1 даёт схему, а не готовые экраны или подключённые сервисы. HTTP-процессы, аудит/outbox команд и идемпотентное сравнение запросов выполняются в последующих Б2–Б8.
- Выплаты имеют только `draft/cancelled`. Юридическая модель, реквизиты, API и подтверждение провайдера — **проверить**; исполнения выплаты нет.
- Отзывы пока нельзя подавать через runtime: нет политики записи до проверки личности участника в Б8. Роль сотрудника не видит непубликованный текст. Окно 14 дней — продуктовый выбор, не правовое утверждение.
- Отмена не возвращает использованный лимит промокода. Возврат права на скидку и пересмотр зачтённой поездки требуют отдельной бизнес-политики.
- Ставки НДС/туристического сбора, БРВ, тип объекта, возрастные правила и сроки регистрации — **проверить** у бухгалтера. В сид не внесены действующие налоговые ставки. Расчёт на стыке дат действия правил и связь старых compliance-таблиц между организациями требуют дальнейшей проверки Б5.
- Документы гостей в эти реестры не копируются. Метаданные споров не предназначены для открытых паспортов/реквизитов; API Б8 должен принимать только разрешённые поля.
- Перед применением к реальным данным: бэкап, проверка дискового места/времени блокировки новых UNIQUE-индексов, прогон на восстановленной копии. В этой итерации миграции проверены на одноразовой БД; сохранённая `views_local` не засевалась.
- Вручную проверить с менеджером/ресепшн/бухгалтером: знаки фолио, закрытие, сторно, видимость объектов и права; с управляющим — каталог услуг, лимиты акций и окно отзывов. Производительность на 500 апартаментов и p95 не подтверждена этими тестами.
