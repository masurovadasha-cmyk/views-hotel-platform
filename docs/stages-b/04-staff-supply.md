# Отдельные рабочие области сотрудников, закупки и склад

Этот блок разделяет интерфейсы по назначенной сотруднику роли и добавляет локальный
операционный учёт закупок и запасов. PostgreSQL Core остаётся источником данных.
Публичный предпросмотр показывает интерфейс; он не становится рабочим сервером
или подтверждённой сессией сотрудника.

## Входы и рабочие области

| Роль в URL | Направление | Рабочая область |
| --- | --- | --- |
| `front_desk` | Ресепшен | Заезды, выезды, бронирование, приглашения гостям, фолио |
| `housekeeper` | Уборка | Назначенные задачи уборки |
| `technician` | Техник | Отдельный интерфейс; рабочий модуль явно отмечен как неподключённый |
| `concierge` | Консьерж | Отдельный интерфейс; рабочий модуль явно отмечен как неподключённый |
| `accountant` | Бухгалтерия | Фолио и сверка возвратов при наличии разрешений |
| `manager` | Управляющий | Операции объекта, номерной фонд, фолио и сверка |
| `owner` | Владелец | Номерной фонд и финансовые рабочие разделы |
| `procurement` | Закупщик | Каталог товаров и внутренние заказы на закупку |
| `warehouse` | Заведующий складом | Приёмка заказа, остатки, выдача и история движений |

В портале появилась пятая карточка **«Закупки и склад»** с двумя отдельными входами.
Карточка сотрудников содержит остальные семь направлений. Все новые подписи
доступны на русском, узбекском и английском языках.

Форматы адресов относительно текущего адреса приложения:

```text
?api=local-core&entry=staff&staffRole=front_desk
?api=local-core&entry=staff&staffRole=procurement
?api=local-core&entry=staff&staffRole=warehouse
?api=demo&entry=staff&staffRole=procurement
?api=demo&entry=staff&staffRole=warehouse
```

`local-core` работает только в предусмотренном приложением loopback-контексте
на порту 4173. Эти адреса не являются ссылками на опубликованный сервер.
Генератор ссылок сохраняет путь приложения, включая префикс GitHub Pages.
При входе через обычный локальный адрес интерфейс выбирается по роли из сессии.

Параметр `staffRole` выбирает страницу, но не выдаёт роль. Запрос входа содержит
только email и пароль. После входа интерфейс сравнивает выбранное направление с
ролью, полученной от Core. При несовпадении рабочие модули не монтируются; сотрудник
может открыть своё направление или выйти. Доступ к каждому модулю требует как
подходящей роли, так и соответствующего серверного разрешения. Backend повторно
проверяет организацию, объект и разрешения при выполнении операции.

Наличие страницы бухгалтера, управляющего или владельца **не снимает прежние
ограничения входа**. Публичная авторизация по email, внешняя отправка писем и
допуск привилегированных ролей с необходимым MFA остаются отдельными условиями
готовности. Синтетические сессии в браузерной проверке не доказывают готовность
реального входа таких сотрудников.

## Схема и права

Миграция `apps/api/db/migrations/0064_supply_and_stock.sql` добавляет:

- Роли `procurement` и `warehouse`; разрешения `supply.read`, `purchase.manage`
  и `stock.manage`. Закупщик получает чтение и управление закупками, склад —
  чтение и складские операции. Существующие пользователи не переводятся в эти роли.
- Таблицы `supply_items`, `supply_orders`, `supply_order_lines`,
  `supply_receipts`, `supply_balances`, `supply_movements`, `supply_commands`.
- Связи организации и объекта в составных внешних ключах, уникальный SKU внутри
  объекта, индексы для выборок объекта, ENABLE/FORCE RLS и политики разрешений.
- Неизменяемые записи движений и команд, допустимый переход заказа
  `ordered → received`, проверку полноты приёмки при фиксации транзакции.
- Обновление остатков через узкий триггер движения с блокировкой товара.
  Остатки не могут стать отрицательными или выйти за пределы PostgreSQL bigint.

Количество — целое число минимальных единиц: `piece`, `gram`, `millilitre`.
API передаёт bigint строками, интерфейс не округляет их через JavaScript Number.
Дробные количества в этом блоке не поддерживаются: например, вес передаётся
целым количеством граммов.

Миграция `0065_supply_staff_auth.sql` расширяет существующий локальный
непривилегированный процесс приглашения и входа двумя ролями снабжения. Она
сохраняет проверки получателя, состояния приглашения, паролей, сессий,
подтверждения ключом и восстановления доступа. Создания настоящих аккаунтов,
смены паролей существующих пользователей и расширения их прав миграция не делает.

Синтетические учётные записи из
`apps/api/db/seeds/supply-auth.synthetic.sql` предназначены для одноразового
тестового стенда, не для загрузки в рабочую установку. Старые миграции не меняются.

## Операции и границы

Core маршруты находятся под `/v1/supply`, локальный cookie gateway — под
`/local-api/supply`. Чтение: `properties`, `items`, `orders`, `stock`, `movements`.
Записи: создание товара и заказа, `orders/:id/receive`, `stock/issue`.
Списки используют постраничное чтение с курсором.

Операционный путь: закупщик создаёт товар и внутренний заказ; сотрудник склада
подтверждает приёмку всего заказа; остаток увеличивается; последующая выдача
уменьшает остаток и сохраняет основание. На заказ допускается до 20 разных позиций.
Одна приёмка соответствует одному заказу. Backend связывает движение с точным
количеством позиции заказа и отклоняет повторную приёмку отдельной командой.

Для каждой записи требуется UUID `Idempotency-Key`. Повтор с тем же ключом,
действующим доступом, тем же сотрудником и содержимым возвращает сохранённый
результат. Конфликт содержимого или исполнителя отклоняется. Изменения данных,
команда, аудит и outbox фиксируются в одной транзакции. UI сохраняет неизменный
ключ и тело при неизвестном результате; повтор выполняется только вручную.

Gateways сохраняют проверки cookie-сессии, CSRF, Origin/Host и разрешённого тела
запроса. Клиент не выбирает actor, организацию или принадлежность чужому объекту.
Операционные маршруты по умолчанию выключены. Для Core одновременно нужны
`NODE_ENV=test`, `VIEWS_LOCAL_REHEARSAL=true` и
`VIEWS_SUPPLY_PILOT_ENABLED=true`; флаг снабжения нужен и локальному gateway.
Не включайте эти флаги на публичном Worker.

**Не реализовано этим блоком:** отправка заказов поставщикам, реестр и договоры
поставщиков, согласование бюджета, оплата, стоимостная оценка остатков, проводки
бухгалтерского учёта, частичные приёмки, возвраты поставщику, перемещения между
складами, инвентаризационные корректировки и интеграции с внешними системами.
Название заказа и его reference — внутренний операционный документ, а не факт
отправки поставщику. Кнопки приёмки и выдачи не создают платёж.

## Запуск проверок

Из корня репозитория с установленными зависимостями:

```sh
npm run typecheck
npm test
npm --prefix apps/api run typecheck
npm run cloud:test:guest-email
```

Последняя команда собирает веб и API, создаёт отдельный PostgreSQL 16,
применяет миграции и тестовые данные, выполняет Core и подключённые браузерные
проверки, затем удаляет только свой одноразовый контейнер. Нужны работающий Docker
и Playwright/Chromium. Не подставляйте в этот процесс адрес постоянной `views_local`.
Постоянная база, её объекты и существующие пользователи для этих тестов не нужны.

Отдельная проверка страниц ролей после обычной веб-сборки:

```sh
npm run build
node scripts/staff-role-entry.browser.cjs
node scripts/guest-link-staff-browser-proof.cjs
```

Это настоящий собранный React-интерфейс с **синтетическими HTTP-ответами**,
без подключения к Core, базе или внешней почте. Скрипты поддерживают аргумент
каталога сборки для изолированной проверки.

Проверка публичного портала:

```sh
npm run build:review
node scripts/access-portal.browser.cjs
```

Review-сборка заменяет обычный `dist`; перед локальными Core-проверками снова
выполните обычную сборку. Не запускайте оба вида сборки параллельно в один каталог.

## Риски и ручная приёмка

1. На тестовых данных пройти закупку и склад двумя разными сотрудниками:
   товар → заказ → подтверждение полной приёмки → выдача → сверка истории и остатка.
   У закупщика не должно быть складских кнопок; у склада — изменения каталога и заказов.
2. Проверить потерю ответа и ручной повтор без второго движения; две одновременные
   выдачи не должны давать отрицательный остаток. Ошибочная запись требует отдельного
   будущего процесса исправления, прямое редактирование истории не предусмотрено.
3. Проверить доступ к чужому объекту и организации, истёкшую сессию, неверное
   направление входа и изменение прав во время открытой страницы.
4. Проверить длинные наименования, большие целые количества, курсоры списков,
   мобильную клавиатуру, три языка, тёмную тему и работу без сети. Сотрудники должны
   подтвердить удобство рабочего процесса; автоматический тест это не заменяет.
5. До реального использования определить, как согласовывать закупки, подтверждать
   поставщика и документ, исправлять ошибки, учитывать стоимость, недостачу и налоги.
   Программный остаток в минимальных единицах не заменяет бухгалтерский складской учёт.
6. Публичный Core, настоящая почта, рабочие учётные записи и production-готовность
   отдельно проверяются и подключаются. Новые интерфейсы сами по себе не означают
   публикацию сайта, новую сборку APK или установку на физический телефон.
