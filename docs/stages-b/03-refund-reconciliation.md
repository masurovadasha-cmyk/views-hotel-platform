# Б3 — сверка возвратов

8 октября 2026, Asia/Tashkent. План подблока: исправить поздние подтверждения возврата, дать бухгалтеру очередь и неизменяемую историю проверки, проверить гонки и права. Допущения: провайдеры не подключены, реальные деньги не отправляются; используются существующие `finance.read` / `finance.manage`, без выдачи новых прав пользователям.

## Поведение

Проверенный callback закрывает `uncertain` и `blocked` так же, как другие незавершённые заявки. Проводка использует сохранённый счёт обязательства (`refunds_payable` после отмены). Закрытие очищает lease/worker; обработчик отправки обновляет только собственную заявку в `processing`. Если callback уже завершил её, запоздавший ответ/таймаут учитывается как `superseded` и ничего не меняет.

Сумма и связанные ID должны совпадать с найденной заявкой. Несколько подходящих заявок или противоречивые ID отклоняются с откатом inbox, транзакции и ledger. Если провайдер сообщает только ранее подтверждённый ID возврата, связь с capture берётся из заявки и сохраняется в `provider_transactions`: восстановление очереди не создаст второй возврат. Неподтверждённый ручной ввод не является callback.

В веб-области сотрудника появился раздел «Сверка возвратов»: фильтры, страницы до50 заявок, детали, последние100 записей проверки, RU/UZ/EN. По умолчанию показаны `uncertain`, `blocked`, `submitted` и просроченные `processing`; чтение ничего не переводит между статусами. Порядок страниц — UUID, не хронология; очередь изменяется между запросами, это не архивный snapshot.

Бухгалтер может записать только «Проверка начата», «Обращение к провайдеру» или «Запрошено подтверждение» и служебный номер обращения (до100 ASCII-символов). Нет действий отправки денег, ручного завершения или повторного запуска возврата. После сетевой ошибки UI повторяет тот же UUID ключ и неизменённое тело; устаревшее состояние требует заново открыть заявку. История проверки не меняет денежный статус.

## Схема и API

Добавочная миграция [0057](../../apps/api/db/migrations/0057_refund_reconciliation_reviews.sql): `payment_refund_reviews`, FK, unique organization/idempotency key, индексы очереди/истории, FORCE RLS, привязка организации/объекта/состояния заявки и автора, append-only trigger. Применённые0001–0056 не менялись. Перед работой прочитан persistent ledger:56 миграций.

Ревизия SHA256 включает состояние доставки, ID, сумму, попытку, lease; API сравнивает её под блокировкой заявки. Точная повторная команда возвращает прежний результат даже после последующего callback. Изменённый payload/автор под тем же ключом конфликтует. Review, audit и outbox записываются одной транзакцией. SQL RLS повторяет права и привязку автора; без актёра доступа к review-реестру нет.

| Метод | Core | Назначение |
| --- | --- | --- |
| GET | `/v1/refund-reconciliation?propertyId=UUID&status=attention&cursor=…` | Очередь конкретного доступного объекта; cursor необязателен и привязан к фильтру |
| GET | `/v1/refund-reconciliation/:id` | Заявка, revision и история |
| POST | `/v1/refund-reconciliation/:id/reviews` | `Idempotency-Key: UUID`, тело `{expectedRevision, action, caseReference}` |

Core требует доверенный транспорт, связанный активный actor и property scope. Локальный BFF `/local-api/refund-reconciliation` берёт propertyId из конфигурации рабочего объекта; клиент не может передать другой объект/актёра. Для деталей Core повторно проверяет доступ к объекту заявки. Сессия PostgreSQL/HttpOnly cookie, CSRF и same-origin сохраняются. Ответы no-store; произвольные provider errors и worker IDs не выдаются. Суммы передаются decimal strings; UI точно форматирует UZS/USD/EUR без преобразования bigint в Number.

## Риски и ручная приёмка

- **Проверить** у выбранных Payme/Click/Uzum продуктов: значения ID в ack/callback, частичные возвраты, подписанный status lookup и окончательность ответа. Противоречие сейчас останавливает обработку; событие нужно повторить после расследования, а не пометить оплаченным вручную.
- Очередь и журнал не заменяют адаптер банковской сверки. `blocked` не перезапускается автоматически после подключения провайдера; `uncertain` не получает resend. Без callback/проверенного lookup такие заявки остаются открытыми. Отдельный контролируемый сценарий разрешения этих случаев ещё требуется.
- Массовый экспорт всей истории и фильтры по периоду/провайдеру остаются программной работой. Нагрузочные p95 и индексы для100000 объектов — Б11.
- В тестовом контуре проверить бухгалтер/читатель/ресепшен и два объекта, сверить ведомость обязательств после callback, повторить действие при потере ответа и убедиться, что запись в истории одна. Номер обращения не должен содержать документы/данные гостя.
- Б3 целиком открыт: конкретные Click/Uzum adapters, банковский authorization/void/capture депозита, реальный фискальный оператор и юридическая схема выплат остаются в плане. Нет публичного выпуска, merge main или нового APK.
