# Б2 / Б6 — подтверждённая привязка существующей брони

Сотрудник с reservation.manage и доступом к объекту выпускает приглашение для
конкретной брони и email. Гость входит в этот email-аккаунт, вводит код, проверяет
объект/даты и отдельно подтверждает привязку. Только после подтверждения бронь
появляется в поездках. Сотрудник видит статус и может отозвать доступ, в том числе
после перезагрузки страницы. Код передаётся вручную после проверки гостя;
автоматической отправки письма нет, интерфейс явно об этом сообщает.

## Схема и решения

Миграция0060 создаёт guest_identity_private.reservation_links: организация,
бронь, снимок primary_guest_id, email получателя, SHA256 кода, сотрудник, ключ
идемпотентности, сроки, принятие и отзыв. ENABLE/FORCE RLS без прямых runtime
политик и REVOKE PUBLIC закрывают таблицу; доступ — через узкие SECURITY DEFINER
функции app с search_path=pg_catalog. Существующий bootstrap выдаёт EXECUTE
ограниченной роли views_app. Индексы: уникальный хеш, (organization_id,command_key),
единственная активная принятая связь на бронь, аккаунт/бронь и бронь/время.

Миграция0061 расширяет проекцию поездок0059. Новое разрешение относится к одной
брони, а не ко всем проживаниям общего CRM-профиля; guest_profiles.user_id не
перезаписывается. Проверяются организации профиля, брони, объекта и разрешения.
Смена основного гостя, назначение профиля другому аккаунту и отзыв закрывают
чтение. Совпадение email или знание номера брони сами по себе ничего не открывают.
Существующее прямое владение профилем из0059 сохраняется независимо; отзыв
приглашения не удаляет такое ранее выданное право.

Код vglk_ создаётся HMAC с отдельным ключом по организации/брони/email/команде.
Повтор выпуска той же команды возвращает тот же код без продления срока;
смена параметров отклоняется. В БД — только хеш. Приглашение действует час до
принятия; принятое разрешение сохраняется до отзыва/смены связи. Параллельные
подтверждения сериализуются блокировками брони/профиля/приглашения. Принятие,
audit и outbox guest.reservation_linked атомарны; отзыв принятой связи создаёт
guest.reservation_unlinked. Повтор не дублирует события. Новый выпуск заменяет
непринятые приглашения с аудитом; активную принятую связь сначала нужно отозвать.

## API и интерфейс

Сотрудник, X-Views-Staff-Session:

- GET /v1/bookings/:id/guest-link — статус без кода;
- POST тот же путь, {email}, Idempotency-Key UUID — выпуск, delivery=manual_handoff;
- POST /v1/bookings/:id/guest-link/revoke, {linkId} — отзыв.

Гость, собственная email Bearer-сессия:
POST /v1/guest-identity/email/reservation-link/preview и /accept, {token}.
Предпросмотр не выдаёт разрешение. Неверный получатель, истёкший/отозванный код
и изменённая бронь возвращают одинаковый GUEST_LINK_INVALID. Лимит30 попыток
за5 минут на аккаунт. GET не подтверждает код.

Локальные cookie-шлюзы используют /local-api/reservations/:id/guest-link и
/guest-api/reservation-link/{preview,accept}. Мутации сотрудника и обе гостевые
операции требуют своей сессии, Origin и CSRF. Произвольные actor/body-поля
отклоняются. Ответы no-store; guest BFF ограничивает поля предпросмотра.
Коды не сохраняются в URL/localStorage и скрываются общим redacting logger.

UI: RU/UZ/EN, отдельное подтверждение гостя, блокировка повторного клика,
ручной повтор после потери ответа; после принятия обновляются поездки.
В ресепшн добавлена панель выдачи, статуса и отзыва. После перезагрузки код
не восстанавливается из GET; можно отозвать приглашение и выдать новое.

## Запуск и тестовые данные

Используются существующие Node22+, Docker/PostgreSQL16 и Chromium, без новых
зависимостей. Проверка запускает и завершает одноразовую БД и серверы:

```sh
npm run cloud:test:guest-email
npm test
npm --prefix apps/api run typecheck
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
npm run build:review
node scripts/access-portal.browser.cjs
```

cloud:test:guest-email сам выставляет NODE_ENV=test, VIEWS_LOCAL_REHEARSAL,
существующие staff/email/trips gates, VIEWS_GUEST_LINK_PILOT_ENABLED=true и
случайный64hex VIEWS_GUEST_LINK_TOKEN_KEY. Стандартный запуск не включает этот
пилот; вне test/local или без флага маршрут закрыт. Ключ не попадает в Git/логи.
При его ротации старый код остаётся пригодным для принятия по хешу, но повтор
выпуска прежней команды отклоняется: требуется новое приглашение.

Синтетические сиды находятся в guest-reservation-link.integration.test.ts и
scripts/guest-reservation-link-browser-proof.cjs; перед записью проверяется
маркер одноразовой БД. Миграции0060/0061 применялись только там. Старые0001–0059
и постоянная views_local не изменялись. Реальные письма не отправлялись.

## Выполненные проверки и ограничения

Изменённое дерево относительно17065b9: Core430 тестов/76 файлов, root267/46,
оба typecheck/build, network154, mail15 — exit0. Новые6 PostgreSQL-групп:
получатель/доступ к одной брони,5 параллельных подтверждений, повтор/замена
приглашений, смена гостя/изоляция/нет прямого доступа, rollback при сбое outbox,
лимит и выключенный/production gate. Три root-группы проверяют шлюзы.

Четыре новые группы настоящего браузер → Core → PostgreSQL проверили гостевую
форму, staff HTTP-выпуск, CSRF, три языка/мобильную ширину, потерю ответа после
принятия, идемпотентность, отзыв, истечение и отказ сотруднику без прав.
Существующие4 группы поездок,4 входа и3 HTTP/SMTP также прошли. Два письма
перехвачены только loopback SMTP. Публичная review-сборка прошла регрессию
четырёх направлений, трёх языков и четырёх ширин без API-запросов.

Форма сотрудника прошла TypeScript/сборку; её полный браузерный сценарий
выдачи/отзыва пока требует ручной приёмки. Автоматически проверены соответствующие
HTTP API и cookie-шлюз, а не весь путь от клика сотрудника до Core.
Проверить вручную: выдачу правильному гостю и процедуру проверки личности,
статус после перезагрузки, клавиатурный фокус/скринридер, тексты носителями,
исторические профили и два одновременных оператора. Отзыв действует при следующем
чтении; уже показанная информация не стирается дистанционно. Производительность
на100000 объектов и доставка реальной почты не проверены.

Публичные веб/APK остались прежними: Core/email пилот не опубликован. Для
реального запуска нужны почтовый провайдер, публичный HTTPS Core и согласованный
операционный процесс. Следующий программный блок — гостевой расчёт и подтверждение
отмены по сохранённой политике; данный блок не завершает весь Б6/продукт.
