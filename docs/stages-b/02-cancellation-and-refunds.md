# Б2 — отмена по тарифу и безопасная очередь возвратов

8 октября 2026, Asia/Tashkent. Подблок продолжает Б2; внешние платежи не подключает.

## Схема и поведение

Миграция `0054_cancellation_refund_limits.sql` добавляет неизменяемый `booking_cancellations` (политика, время решения, удержание, реально собранная сумма, возврат, актор, ключ) и `cancellation_capture_limits` (предел возврата по каждому уже полученному списанию). Составной FK связывает бронь с организацией, объектом и валютой; проверка списания связывает его с нужной бронью. FORCE RLS проверяет staff permission/property scope; существующий внутренний recovery без staff-контекста получает чтение в своей организации.

`POST /v1/bookings/:id/cancel`, UUID `Idempotency-Key`, существующая авторизованная staff identity. Только `NODE_ENV=test`, `VIEWS_LOCAL_REHEARSAL=true`, `VIEWS_CANCELLATION_PILOT_ENABLED=true`; по умолчанию закрыто. Новый доступ/роль не создаётся. BFF/кнопка отмены ещё не добавлены; эта итерация проверяет Core API/service boundary.

Команда работает для подтверждённой брони до заезда. Использует время БД и замороженные строки/политику, не принимает сумму возврата от клиента. Из цены вычитается положенный по тарифу возврат — это удержание. Из реально собранных денег возвращается только сумма сверх удержания: цена 100, удержание 50, предоплата 80 → возврат 30; предоплата 30 → возврат 0. Задолженность за удержание сверх оплаты автоматически не взыскивается.

Блокировки идут как у платёжных callback: intents, затем бронь. Сериализация ключа защищает повторы. Отмена, освобождение дат, снимок лимитов, бухгалтерская переклассификация возврата, очередь возвратов, аудит и outbox выполняются в одной транзакции. Повторная команда возвращает прежний результат; отзыв права проверяется перед повтором. Самостоятельная смена цены после бронирования не меняет условия отмены.

Recovery читает лимит и не превращает частичный возврат в полный. Новое списание после отмены не относится к старому лимиту и полностью возвращается как late capture. Незавершённая заявка на возврат удерживает операцию до сверки, даже если callback неполный. Отсутствие возврата не помечает платёж `refund_pending`.

## Неизвестный результат отправки

`PaymentRefundWorkerService` теперь различает:

| Результат | Состояние | Повтор |
| --- | --- | --- |
| Провайдер принял запрос | submitted | Ждать подтверждения; ledger меняется по проверенному callback |
| Адаптер не подключён | blocked | Только после подключения и решения оператора |
| Доказано, что запрос не отправлен (`RefundNotSentError`) | pending | Отложенный повтор с тем же ключом |
| Таймаут, неизвестная ошибка/ответ | uncertain | Автоматического повтора нет |
| Lease processing истёк | uncertain | Сверка, поскольку старый worker мог успеть отправить деньги |

Произвольное сообщение провайдера не сохраняется как ошибка: используется фиксированный диагностический код. После ручной сверки решение об операции должно опираться на статус/идентификатор у провайдера; нельзя просто сбрасывать uncertain в pending. Интерфейс такой сверки ещё предстоит в Б3/Б8/Б11.

## Проверка и воспроизведение

Из корня `npm run cloud:test:core`; из `apps/api` — `npm run typecheck && npm run build`. Миграцию применяет обычный поддерживаемый запуск, без reset/seed сохранённой БД.

- Четыре теста распределения возврата: частичная предоплата, предыдущий возврат в арифметике, bigint, некорректные суммы/дубли.
- Семь интеграционных тестов PostgreSQL: замороженный частичный возврат и повторная сверка, late capture, предыдущий refund workflow, конкуренция ключей, отзыв доступа/default-off, сохранённый uncertain/истёкший lease, полный откат при ошибке аудита.
- Пять тестов классификации отправки, дополненных настоящими PG-проверками очереди. Все провайдеры в этих тестах — **явные синтетические адаптеры**, без сети.
- Общий Core: 375 тестов / 70 файлов; дополнительно семь rollback SQL-групп Б1. Root: 245/40; Core/web сборки и typecheck, network139, mail15 — успешны. Финальный Core журнал `/tmp/views-b2-release-core.log`.
- Сохранённая локальная среда: 54 миграции, пять новых; auth 13 групп / 32 HTTP, браузерный вход/hold/reload/release успешны. Restore после обновления: 85 таблиц, 25 зашифрованных тестовых документов, 17 turnovers, совпадение всех digest. Это не доказательство восстановления production или достижения RTO/RPO.

## Риски и ручная приёмка

Реальные адаптеры, поддержка частичных возвратов Payme/Click/Uzum, договоры и подтверждения API — **проверить**. Payme sandbox ранее прямо отклонял инициативный refund и требовал Merchant API cancellation; эта интеграция не стала полноценным каналом частичных возвратов. Книга учитывает обязательство возврата, но признание удержанной комиссии/выручки и фискализация требуют Б3 и бухгалтера.

Бронь с любым уже существующим refund workflow, окончательной выплатной экономикой, несогласованными суммами/периодами или начавшимся проживанием требует сверки и не изменяется автоматически. Ранний выезд относится к Б4. Сервис пока пилотный; гостевая принадлежность брони, интерфейс отмены и доставка уведомлений — последующие подблоки.

Вручную: сопоставить удержания с утверждённой политикой; проверить две вкладки/повтор после потери ответа; проверить uncertain без повторной отправки; сверить реальные отчёты провайдера с журналом, лимитами, чеком и выпиской гостя. Реальных операций в этой итерации нет.
