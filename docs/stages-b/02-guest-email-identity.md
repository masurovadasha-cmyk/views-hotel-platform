# Б2 — гостевой email-вход: API и изоляция сессий

8 октября 2026, Ташкент. Дополнение к SMS-идентичности и существующему входу
сотрудников. Это завершённый локальный API-блок, **не включение входа на публичном
вебе/APK**. Для публичного входа ещё нужны Core-хостинг, почтовый транспорт и
гостевой интерфейс, подключённый к этим новым API вместо старого Pages/D1 auth.

## Решения и схема

Миграция `0058_guest_email_identity.sql` добавляет закрытые таблицы
`guest_identity_private.email_challenges` и `email_sessions`, индексы по адресу,
сроку действия и пользователю, а также пять ограниченных функций `app.*`.
Существующие миграции и SMS/сотруднические сессии не изменяются.

Это глобальная идентичность пользователя, поэтому у таблиц нет фиктивной
организации. Защита — закрытая схема, запрет прямого доступа runtime/PUBLIC и
SECURITY DEFINER-функции с фиксированным search_path. В SQL нет создания или
изменения членства, профиля гостя организации и бронирований. Tenant RLS на
бизнес-данных сохраняется. Синтетические данные создаются только тестами в
одноразовой БД; административные проверки откатываются.

Ссылка: случайный 256-битный секрет с отдельным HMAC-ключом, 15 минут с момента
выдачи, одноразовый обмен POST. В БД хранится HMAC, в HTTP-ответе на запрос
секрета нет. Новая выдача после 60 секунд отменяет предыдущую. Ограничения:
20 запросов с одного сетевого идентификатора в час, 5 на адрес в час, 60 обменов
за 5 минут; пять неверных попыток блокируют конкретную ссылку. Строковая
блокировка обеспечивает одного победителя при параллельном обмене.

Состояния доставки `pending → accepted | uncertain`, отдельно `superseded`.
Тайм-аут/неопределённый результат не разрешает вход; позднее подтверждение не
восстанавливает отменённую/просроченную ссылку. `provider_accepted` означает
принятие транспортом, а не доставку в ящик и не подтверждение владельца адреса.
Реестр адаптеров по умолчанию пуст и возвращает `GUEST_EMAIL_NOT_CONNECTED`.
Сетевой SMTP-код не добавлен в транзакционный Core.

Гостевая сессия действует 7 дней и хранится отдельно от SMS и staff. Смена email,
блокировка пользователя, истечение или выход прекращают доступ. Email уже
существующего сотрудника даёт только гостевую сессию: пароль/приглашения/MFA и
права сотрудника не заменяются. Нормализация учитывает регистр и пробелы вокруг
адреса; точки и `+tag` не удаляются. Internationalized local-part пока отклоняется.

## Контракт API

| Метод | Путь | Тело / авторизация |
| --- | --- | --- |
| POST | `/v1/guest-identity/email/request` | `{email, locale}`; ru/uz/en |
| POST | `/v1/guest-identity/email/exchange` | `{challengeId, token}` |
| GET | `/v1/guest-identity/email/session` | `Authorization: Bearer vges_…` |
| POST | `/v1/guest-identity/email/logout` | `{}` и тот же Bearer |

Ответы успешной авторизации/профиля имеют `Cache-Control: no-store`. Токены
`vgel_…`, `vges_…`, а также существующие `vgs_…` скрываются redacting logger.
Поля `role`, `organizationId` и другие лишние поля запроса отклоняются.
Секрет ссылки должен находиться во fragment, который будущий клиент удалит из
адресной строки; GET сам по себе не обменивает ссылку, включая почтовые сканеры.

## Запуск и доказательства

Используйте уже настроенную облачную среду: Node 22+, Docker, зависимости из
lock-файлов и доступный закреплённый PostgreSQL-образ. Из корня:

```sh
npm --prefix apps/api run typecheck
npm --prefix apps/api run build
VIEWS_GUEST_EMAIL_HTTP_PROOF=true npm run cloud:test:core
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
```

Runner создаёт собственный PostgreSQL-контейнер и удаляет его после проверки;
`views_local` не сбрасывает и не использует. HTTP-доказательство поднимает
скомпилированный NestJS Core и SMTP-приёмник на случайных loopback-портах.
Письмо фактически проходит через Nodemailer/SMTP, но остаётся в памяти локального
приёмника и адресовано только `@views.invalid`. Это явно тестовый адаптер,
не внешний почтовый провайдер. Он регистрируется только внутри proof-скрипта.

Feature flags в proof: `NODE_ENV=test`, `VIEWS_LOCAL_REHEARSAL=true`,
`VIEWS_GUEST_EMAIL_PILOT_ENABLED=true`, отдельный случайный
`VIEWS_GUEST_EMAIL_TOKEN_KEY`. Скрипт сам создаёт/восстанавливает значения и не
печатает секреты. Одних флагов недостаточно без зарегистрированного транспорта.
Рабочие и production-конфигурации по умолчанию не активируют модуль.

Проверено на изменённом дереве относительно `8ed9b0c`: Core417/74 файла;
12 новых email-сценариев, тест редактирования логов; административные проверки
сроков, повторной выдачи и существующего staff-email; HTTP/SMTP 3 группы,
1 синтетическое письмо. Проверены повторный обмен, пять одновременных обменов,
конкурентные запросы, неверные попытки, неопределённая/запоздалая доставка,
недоступность private-таблиц, отзыв сессии, смена адреса и отсутствие staff-прав.
Typecheck/build API прошли; сетевой анализ150 файлов без нарушений и mail15
прошли. CI Production Core выполняет миграцию, SQL-проверки, API-тесты и
HTTP/SMTP-доказательство на своей временной БД.

## Что проверить перед публичным включением

- Подключить выделенный почтовый worker/провайдер через существующую сетевую
  границу, настроить отправителя, SPF/DKIM/DMARC и обработку неопределённой
  доставки. Внешние письма и автоматические повторы в этом блоке не включены.
- Подключить гостевой UI и HTTPS gateway: безопасная передача/хранение сессии,
  обработка fragment, истечения ссылки, выхода и недоступной сети. До этого
  публичная кнопка честно показывает, что email-вход не подключён.
- Провести ручную проверку на подтверждённых тестовых ящиках и телефоне;
  установить сроки удаления адресов/истёкших challenges и подтвердить правила
  хранения данных. Автоматическая очистка и production retention пока не включены.
