# Б4/Б7: частичная приёмка и инвентаризация

Закупщик сохраняет заказ, а кладовщик указывает фактически полученные количества.
Недопоставленная часть остаётся открытой. Инвентаризация сравнивает учётный
остаток с физическим пересчётом; изменение проводится только после просмотра
разницы и отдельного подтверждения с причиной.

## Совместимая схема

0066 сохраняет прошлые полные приходы и создаёт неизменяемые строки поставки
supply_receipt_lines. Заказ может иметь несколько приходов и состояние
partially_received. Блокировка заказа, общий объём по каждой строке и отложенная
проверка целостности не позволяют принять больше заказанного или записать
неполную историю. Старые миграции0064/65 не меняются.

0067 добавляет supply_stocktakes, ссылку корректировки на пересчёт и revision
остатка. Каждое движение меняет revision, даже если последовательность выдачи
и приёмки вернула прежнее количество. Нулевой пересчёт сохраняет факт наблюдения.
RLS по организации/объекту, автор, неизменяемая история, audit/outbox и команды
повторов сохраняются. Права только stock.manage; новые полномочия не выдаются.

## API

- GET /v1/supply/orders: receivedQuantity и remainingQuantity на каждой строке.
- POST /v1/supply/orders/:id/receive: {lines:[{itemId,quantity}]} с UUID
  Idempotency-Key. Старое {} совместимо и означает весь оставшийся объём;
  новый интерфейс всегда отправляет явно выбранные количества.
- POST /v1/supply/stocktake/preview: propertyId, itemId, countedQuantity, reason.
  Не меняет остаток. Возвращает ожидаемые количество/revision и разницу.
- POST /v1/supply/stocktake/confirm: те же поля плюс expectedQuantity и
  expectedRevision, обязательный UUID Idempotency-Key. При устаревании —409
  STOCKTAKE_STALE без записи; оператор заново загружает и проверяет данные.

Количества передаются строками минимальных единиц piece/gram/millilitre.
Число при приёмке положительное, при пересчёте допускается0; предел bigint.
Дробные килограммы/литры надо перевести в граммы/миллилитры до ввода.
UI на RU/UZ/EN, ручной повтор исходной команды после неизвестного результата,
никаких автоматических складских изменений при восстановлении сети.

## Запуск

```sh
npm run cloud:test:guest-email
npm test
npm --prefix apps/api run typecheck
```

Первый runner создаёт маркированную одноразовую PostgreSQL, применяет миграции
и тестовые записи, затем запускает Core и настоящий браузерный сценарий.
Постоянная views_local не сбрасывается и новые миграции туда не применяются.
VIEWS_SUPPLY_PILOT_ENABLED работает только при существующих local/test условиях.

Новые проверки: приход4+6, отказ превышения, конкуренция приёмок, смешанные
строки и откат; пересчёт вверх/вниз/в0, нулевое изменение, устаревшая revision,
конкуренция, неправильный автор, прямые SQL нарушения и атомарный откат.
Сквозной браузер проверяет потерю ответов, ручной повтор, изменившийся остаток,
права, CSRF и совместимость полного прихода. Точные результаты — в статусе
поставки после прогона, а не заявление о проверке рабочего склада.

## Риски и ручная приёмка

- Проверить физическую поставку по каждой позиции перед подтверждением.
- Пересчёт проводится по одной позиции и объекту. Массовая ведомость, независимый
  утверждающий сотрудник и блокировка физического движения на время пересчёта
  пока не реализованы. Причина и автор остаются в истории.
- После неизвестного ответа повторить ту же команду. После перезагрузки сначала
  проверить историю: ключ формы хранится в памяти, а не в постоянном журнале UI.
- Проверить на телефоне RU/UZ/EN, выбор единиц, частичную приёмку, нулевой
  пересчёт и возобновление после потери связи.
- Денежная оценка, налоги, проводки стоимости, поставщики/оплата, возвраты
  поставщикам и перемещения между складами остаются отдельными задачами.
- Публичные веб/APK — явно обозначенный демонстрационный интерфейс. Реальные
  складские операции и вход требуют развёрнутого PostgreSQL Core и доступа.
