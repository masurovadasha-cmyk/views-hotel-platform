## План, допущения и результат

Задача этого этапа — просмотр занятых интервалов и ручное закрытие действующего
номера на ремонт или собственные нужды с последующим снятием такой блокировки.
Поддерживается собственная организация `platform`, объект `active`, страна UZ,
timezone Asia/Tashkent. Вход и выдача привилегированных ролей не расширяются.
Это список интервалов календаря, ещё не drag-and-drop шахматка PMS.

Простое решение: использовать существующую общую таблицу inventory_periods и
её EXCLUDE, а не заводить второй календарь с отдельной проверкой пересечений.
Отдельный флаг сохраняет границу локального этапа до приёмки входа владельца.

## Схема — совместимое использование, без новой миграции

- `organizations.type = platform` → `properties` → `units`.
- `inventory_periods`: organization_id/property_id/unit_id, kind, source_ref,
  stay_period `tstzrange [start,end)`. Новые записи — `maintenance` или `host_block`.
- Существующее ограничение `inventory_periods_no_overlap` запрещает пересечение
  любых видов периодов одного юнита, в том числе с payment_hold/reservation.
- `audit_log`: кто создал/снял блокировку, состояние до/после.
- `outbox_events`: owner.calendar_blocked / owner.calendar_unblocked; снимок
  периода, хеш команды, результат, ключ повтора организации/сотрудника.

Новые миграции и изменения применённых checksum не понадобились. В CI найден
старый ручной список, заканчивавшийся 0046: production-core.yml теперь применяет
всю упорядоченную цепочку, как одноразовый cloud runner, включая 0047–0049.
YAML разобран, эквивалентная полная цепочка выполнена локально; успешный запуск
этого SHA в GitHub Actions ещё не утверждается.

## Код и поведение

Core: `apps/api/src/owner/owner-calendar.input.ts`, `owner-calendar.service.ts`;
маршруты в OwnerInventoryController, существующие gateway и StaffSessionGuard.
UI: `src/features/local-core/OwnerCalendarWorkspace.tsx`, кнопка в списке
действующих объектов кабинета владельца. RU/UZ/EN, 375 сообщений staff-каталога.

- GET `/v1/owner-inventory/:propertyId/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD`:
  просмотр до 62 дней, конец исключён, до 100 номеров/1000 интервалов; неполный
  результат явно помечается и не выдаётся за подтверждённую доступность.
- POST того же пути с Idempotency-Key: `{action:'block',unitId,kind,start,end}`
  либо `{action:'unblock',periodId}`. Время строго `YYYY-MM-DDTHH:mm+05:00`,
  реальные календарные даты, длительность не более 366 дней. Посторонние поля
  authority, виды financial/external и запросы с неразрешёнными query отвергаются.
- Создание/снятие, аудит и outbox — одна транзакция. Существующая authority
  блокируется; организация/объект проверяются на сервере, номер блокируется
  перед записью. Одновременный hold и ручная блокировка не занимают обе даты.
- Снять можно только запись, совпадающую с собственным исходным событием,
  source_ref, видом, юнитом и точным периодом, без reservation_id/expires_at.
  Нельзя снять бронь, hold, внешний календарь, чужой объект или изменённую запись.
- Даже истёкший, ещё не освобождённый hold показывается как ожидающий освобождения.
  Этот инструмент не подменяет согласование/expiry worker и не удаляет его.
- Потеря ответа замораживает форму и ключ до повторного подтверждения. Старый
  replay после снятия не создаёт блокировку заново; UI сообщает о выполненной
  ранее команде и загружает текущее состояние. Снятие требует подтверждения.

## Запуск проверок без хостинга и домена

Из корня установленного репозитория:

```sh
npm run build
npm --prefix apps/api run typecheck
npm --prefix apps/api run build
npm test
npm run cloud:test:core
npm run test:workspaces
npm run cloud:start
npm run cloud:status
```

Core runner сам создаёт и удаляет только свой одноразовый контейнер. Никогда не
применять его CI fixtures к views_local. Браузерная проверка календаря перехватывает
HTTP и читает dist; настоящий привилегированный пользователь ей не нужен.

Feature flag `VIEWS_OWNER_CALENDAR_ENABLED=true` нужен и Core, и gateway вместе
с существующими NODE_ENV=test и local-rehearsal. Обычный запуск оставляет его
выключенным. Список объектов использует прежний owner draft flag. Это технические
условия для отдельного разрешённого стенда, не команда выдавать существующей
учётной записи дополнительные права. Контракт штатного запуска не менялся;
новый onboarding config draft не нужен.

## Риски и ручная приёмка

- Не активированы настоящий вход владельца/хоста, публичный сервер и продажи.
- Только Ташкент/UZ и собственный фонд; другие страны/host organizations требуют
  отдельной политики доступа и timezone adapter. Просмотр ограничен; пагинация,
  шахматка, перенос номера, сезонные цены и синхронизация каналов — следующие этапы.
- Фактические p95, 100000 объектов, 99.9% и WCAG не подтверждены этим тестом.
  Build предупреждает о JS chunk >500 kB; загрузку/разбиение и слабую сеть ещё
  предстоит измерить. Outbox lookups требуют профилирования на больших данных.
- Новый Android APK не собирался и не публиковался.
- После подключения разрешённого входа владельца вручную проверить: нужный объект
  и номер; UTC+5 и границу окончания; конфликт с бронью; отмену подтверждения;
  медленную сеть/повтор; другое окно браузера; неполный календарь; клавиатуру,
  screen reader и переводы. Не использовать реальные гостевые данные для фикстур.

Правовые ставки, платежи и рыночные оценки из полного ТЗ помечены «проверить» в
PRODUCT_REQUIREMENTS.md; этот этап не подтверждает эти внешние факты.
