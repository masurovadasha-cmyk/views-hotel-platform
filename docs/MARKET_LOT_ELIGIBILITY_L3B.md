# L3b — годные партии и порядок выбора перед резервированием

## Приёмка
1. В staff API нет партий с истёкшим сроком или нулевым остатком.
2. Срок действует до конца календарного дня объекта, согласно ранее принятому решению.
3. Порядок: serviceId, ближайшая дата, маркировка; неизвестная дата последняя.
4. Неизвестная партия остаётся для ручной проверки; автоматического выбора нет.
5. Чтение не меняет склад, цену и резерв. Серверный guard выдачи остаётся обязательным.

Оба режима выдачи (свежая сверка и текущий ledger) применяют app.lot_date_allowed из migration0114.
Дата берётся по statement_timestamp и properties.timezone; клиентские часы не участвуют.
UI RU/UZ/EN объясняет порядок и ручное подтверждение. Новых миграций и зависимостей нет.

## Границы и следующие срезы
Это подготовка к резерву по партиям, а не сам резерв и не автоматический FEFO.
Каталог пока резервирует общий SKU; наличие негодных остатков может привести к невозможности выдачи.
Одна партия должна покрывать всю позицию; выбор нескольких партий не включён.
Следующий срез: схема привязки резерва к партии и проверки конкуренции под общим item lock, без включения неполного режима.
Затем создание/замены/отмена/выдача/сверка должны атомарно учитывать эту привязку; включать только после проверки всех путей.
Публичные веб/APK и Canva-статусы не меняются.
