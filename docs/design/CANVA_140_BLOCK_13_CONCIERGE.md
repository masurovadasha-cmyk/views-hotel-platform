## Данные и переходы

Миграции 0094–0098 расширяют общий service_catalog/service_orders, добавляют
concierge_requests и append-only concierge_messages, scoped FK, индексы и FORCE RLS.
Прямые runtime-записи в новые таблицы запрещены. Изменения — только через функции
с проверкой действующей гостевой/служебной сессии и принадлежности брони/объекта.

Поручение: requested → working → answered → closed. Гость может отменить открытое
поручение; это не отменяет внешнюю бронь. Вопрос гостя после ответа возвращает
поручение в working. Сотрудник может вернуть working в общую очередь. Управляющий
может освободить чужое назначение, но для ответа сначала должен взять поручение.
Одновременно взять одно поручение двум сотрудникам нельзя.

Общий заказ сохраняет accepted во время работы консьержа. При закрытии гостем
атомарно проходит in_progress → completed. Это сохраняет существующие ограничения
общего движка и возможность отмены бесплатного поручения до закрытия.
Триггер не позволяет напрямую завершить или отменить общий заказ в обход поручения.

Сумма заказа нулевая. Бюджет хранится отдельно как bigint в минимальных единицах и
не является разрешением на покупку. Фолио, платежи и склад не меняются.
Каталог должен быть явно включён оператором для объекта: active=true,
execution_kind=concierge, price_minor=0 и валюта проживания. Автоматического
включения для реальных объектов нет.

Каждая запись требует UUID Idempotency-Key и текущей revision. Повтор после
потери ответа использует исходный ключ и тело. Права повторно проверяются после
блокировки; отозванная связь с бронью не даёт получить старый результат. Audit и
outbox пишутся в одной транзакции. Чужие membership/user ID гостю не выдаются.

## API и интерфейсы

Гость: GET/POST `/v1/guest-identity/email/services/concierge`,
POST `/v1/guest-identity/email/services/concierge/:id/actions`.
Список требует reservationId; создание — reservationId, category, partySize
(1–50), budgetMinor (строка), requestedFor (UTC), message (1–500 символов).
Команды гостя: message, close, cancel. Команды сотрудника: claim, release,
message, answer. Команды содержат expectedRevision; message/answer также message.

Сотрудник: GET `/v1/service-orders/concierge?propertyId=...`,
POST `/v1/service-orders/concierge/:id/actions`. Требуется concierge.work или
reservation.manage и актуальный scope. Обычный консьерж видит общую очередь и
свои назначения; диспетчер — все поручения объекта. URL не меняет роль.

Cookie BFF фиксирует объект, проверяет CSRF и пропускает только разрешённые поля
гостевого ответа. Списки используют UUID cursor и страницы по 2 поручения с полной историей: это сохраняет существующий лимит
гостевого шлюза 128 KiB даже при длинных сообщениях. История ограничена 100
сообщениями и 16 000 байт UTF-8 текста на поручение; затем предлагается обратиться
на ресепшен. В дальнейшем очередь и пагинированная история будут разделены.
Закрытие/отмена остаются доступны. Вложения и паспорта не принимаются.

Интерфейсы RU/UZ/EN используют общую Light/Dark тему. При потере сети отправка
блокируется, при неизвестном результате навигация/выход заблокированы до ручного
повтора. Переписка не сохраняется в localStorage. Дата формы отображается в часовом
поясе устройства; API получает UTC. Автообновление и push пока не включены.

## SLA и ограничения

15 минут до ответа — **гипотеза пилота**, не измеренный SLA и не обязательство
партнёра. Дедлайн фиксируется сервером; после нового вопроса на уже отвеченное
поручение начинается новый срок. Просрочка видна при обновлении списка. Очередь
не сбрасывает срок при смене исполнителя. Смены, паузы, ночной режим, лестница
эскалации и KPI первого ответа требуют следующего блока.

До запуска проверить с управляющим покрытие смен и реальные p50/p90 ответа;
с юристом — обработку переписки, срок хранения и согласия. Платная партнёрская
услуга требует отдельного согласования, условий отмены и финансового процесса.

## Запуск и ручная приёмка

Использовать существующий локальный запуск из блока 7. Нужны миграции до 0098,
NODE_ENV=test, VIEWS_LOCAL_REHEARSAL=true, VIEWS_SERVICE_ORDER_PILOT_ENABLED=true
и существующие флаги гостевой/служебной аутентификации. Вне локального пилота
Core отклоняет маршруты. Пользовательскую views_local не сбрасывать и не заполнять
синтетическими сидами.

Автономная проверка (одноразовый PostgreSQL и loopback SMTP):

```sh
npm run build
npm --prefix apps/api run build
VIEWS_GUEST_EMAIL_HTTP_PROOF=true VIEWS_GUEST_EMAIL_BROWSER_PROOF=true node scripts/cloud-core-tests.cjs
```

Ручная проверка: два сотрудника на одно поручение; отзыв scope; большой бюджет;
длинный текст; отмена после ответа; новый вопрос после ответа; закрытая бронь;
RU/UZ/EN, Light/Dark, клавиатура и узкий экран; отсутствие автоматической покупки.
Публичные веб/APK не обновляются этим локальным блоком.
