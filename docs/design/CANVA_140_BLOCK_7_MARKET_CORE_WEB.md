# Canva 140 — V Market, складской резерв и выдача

Базис: `6109738`. Источник — переданный PDF, SG-MK-001–004, SD-MK-001–002,
SS-MK-001–002. Реализуется собственный склад: корзина → резерв → сборка →
проверка → физическая выдача → подтверждение гостем → одно начисление.
Публичный веб/APK 0.14.0-preview не меняется этим блоком.

## Допущения и границы

Первый рабочий режим — упакованные товары, учитываемые целыми штуками. Только
активные товары, явно связанные с service_catalog, доступны гостю. Розничная
цена не выводится из закупочной. Не публикуется весь склад. Цены каталога считаются
окончательными для этого локального сценария; новые налоги/фискальные чеки и
юридические правила не выдумываются. Проверить их с бухгалтером до запуска.

Корзина: 1–20 разных товаров, 1–50 единиц каждого; одна валюта проживания.
Гость явно соглашается с составом и суммой. Цена и состав замораживаются на
общем service_order. Доставка стоит 0 в этом режиме выдачи, гарантированного
временного окна нет. Замены запрещены, внешние курьеры, ETA, QR-коды и платная
доставка ещё не подключены. Это не полная приёмка SG-MK-003 или SP-MK-001.

## Миграции и безопасность

- 0080: связь market_products между каталогом услуг и supply_items; market_orders
  и market_order_lines с составными FK, индексами и FORCE RLS. Прямых runtime
  записей в эти таблицы нет. Триггер supply_balances защищает резервы от обычного
  списания и инвентаризации. Новых прав существующим сотрудникам не добавлено.
- 0081: каталог и оформление корзины по гостевой сессии и владению бронью.
  Проверяются статус проживания, текущая ревизия товара, валюта и точная сумма.
  Блокировки всех товаров берутся в одном порядке. При нехватке одной позиции
  откатывается вся корзина, без частичного резерва.
- 0082: общий журнал идемпотентности, аудит/outbox; сборка и выдача требуют
  `stock.manage` и действующую сессию склада. Чек-лист: состав/количество,
  сроки годности, упаковка. При выдаче резерв освобождается и записываются
  обычные supply_movements в одной транзакции.
- 0083: ограниченные списки для гостя и склада; код юнита только в рабочей
  очереди; завершить service_order без соответствующего фолио запрещено.

Физический остаток, резерв и доступное количество читаются в одном снимке БД.
Складская карточка показывает все три; отрицательная доступность запрещена
триггером. Учёт закупок, приёмки и инвентаризации остаётся в прежнем модуле.
При фактической недостаче ниже резерва сотрудник должен разобраться с заказами
и отменить невыполнимые резервы перед подтверждением инвентаризации. Автоматически
занижать резерв или заменять товары запрещено.

## Переходы

| Действие | Кто | До → после | Остатки / деньги |
|---|---|---|---|
| request | Гость | — → reserved | Резерв, цена зафиксирована, начисления нет |
| pick | Склад | reserved → picking | Резерв сохраняется |
| ready + checklist | Склад | picking → ready | Резерв сохраняется |
| handover | Склад | ready → handed_over | Одно списание каждой позиции |
| confirm_receipt | Гость | handed_over → completed | Одно начисление полной суммы |
| cancel | Гость | reserved → cancelled | Резерв освобождён, без списания/начисления |
| cancel | Склад | reserved/picking/ready → cancelled | То же, до передачи |

После передачи отмена и автоматическое возвращение товара в остаток запрещены.
Возврат товаров, недовоз и претензии требуют отдельного следующего процесса.
Закрытое фолио не открывается обходным путём: начисление отклоняется для сверки.
Дубликаты команд возвращают прежний результат только после повторной проверки
доступа. Старые ревизии и старые цены не принимаются.

## API и интерфейсы

Гость: `/v1/guest-identity/email/services/market`:
`GET /catalog?reservationId=…`, `GET ?reservationId=…`, `POST /`,
`POST /:id/actions`. Запрос создания: reservationId, expectedTotalMinor (строка),
lines[{serviceId,quantity,expectedRevision}]. Остальное вычисляет сервер.

Склад: `/v1/service-orders/market`: `GET ?propertyId=…`, `POST /:id/actions`.
Оба списка ограничены 50 строками и курсором. Действия используют expectedRevision,
UUID Idempotency-Key; ready дополнительно требует полный checklist.

Cookie BFF ограничивает маршруты, origin/CSRF и параметры. Объект рабочей очереди
берётся из конфигурации локального стенда, не из произвольного запроса браузера.
В гостевом ответе вырезаются внутренние itemId и закупочная информация.

React: отдельная корзина в поездке и очередь в кабинете склада; RU/UZ/EN,
общие темы, состояния загрузки/ошибки/offline. Неизвестный результат сохраняет
тот же ключ и тело для ручного повтора; до сверки переход из поездки блокируется.
Повтор не хранится после принудительного закрытия вкладки — сверить историю.

## Запуск и проверка

Зависимости прежние, новых пакетов нет. На облачном checkout с Node и Docker:

```sh
npm run build
npm --prefix apps/api run build
npm test
VIEWS_GUEST_EMAIL_HTTP_PROOF=true VIEWS_GUEST_EMAIL_BROWSER_PROOF=true node scripts/cloud-core-tests.cjs
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
```

Runner создаёт одноразовую БД PostgreSQL 16, применяет миграции и защищённый
`market.synthetic.sql`, затем удаляет только свой контейнер. Постоянная
`views_local` не используется. Синтетический начальный остаток — тестовые данные,
не инструкция обходить приёмку на реальном складе.

Флаги сервиса: NODE_ENV=test, VIEWS_LOCAL_REHEARSAL=true,
VIEWS_SERVICE_ORDER_PILOT_ENABLED=true, VIEWS_MARKET_PILOT_ENABLED=true;
для склада — существующий VIEWS_SUPPLY_PILOT_ENABLED. Без отдельного флага
маркет недоступен. Публичный Core и новые реальные роли не включаются.

## Что ещё проверить и реализовать

- Полная визуальная сверка PDF в обеих темах, экранный диктор и физический Android.
- Публикация товаров и редактирование розничных тарифов через кабинет; сейчас
  каталог настраивается администратором БД, а тестовый каталог — только фикстурой.
- Выбор объекта рабочей очереди на многoобъектном стенде, назначения сборщика,
  курьера, слоты/мощность, SLA и завершение забытых резервов. Сейчас резерв
  действует до явной отмены или выдачи; автоматическая периодическая задача не добавлена.
- Замены с отдельным согласием, недовоз, возвраты, фото, партии и сроки годности
  в товарном учёте. Сейчас срок годности подтверждает сотрудник чек-листом.
- Санитария, ограничения товаров, налоги, чеки и условия продажи — проверить
  с юристом/бухгалтером. Алкоголь и табак в пилот не добавлять.

Вопросов, блокирующих дальнейшую локальную разработку, нет.
