# Canva 140 — корректировки фолио и физический возврат V Market

Базис: `46896f5`. Расширены SG-MK-004, SD-MK-002, SS-MK-001 и применимая
финансовая область SD-GN-008. Это локальные процессы, не полная приёмка PDF.

## Блок 11: частичное уменьшение начисления

Бухгалтер видит завершённые заказы своего объекта. Вводит сумму и причину для
гостя, подтверждает действие. Core добавляет отрицательную запись `credit` в
открытое фолио, связанную с исходным начислением. Исходная запись сохраняется.
Сумма всех корректировок не превышает начисление; источник с проводкой ledger,
сторнированный источник и закрытое фолио корректировать здесь нельзя.
Сторно исходной записи после частичной корректировки также запрещено.

Право `finance.manage` обязательно; склад не может уменьшать начисления.
Каталог финансовых заказов требует `finance.read`. Сессия и scope повторно
проверяются после блокировок. Гость видит сумму уменьшения, итог и последние
20 причин. Полный журнал записей доступен через фолио с пагинацией.

**Это не перевод денег гостю.** Провайдерские возвраты, фискальные коррекции и
книга двойной записи этим процессом не выполняются. Блок работает только в
существующем локальном пилоте operational_charges. Юридическую схему и
корректировку чеков проверить с бухгалтером до запуска реальных оплат.

Миграции 0088–0090: тип записи `credit`, scoped FK `credit_of`, реестр
`market_credits` с FORCE RLS и запретом прямой runtime-записи, проверки лимита
и защиты от двойного сторно. Реестр и фолио связаны отложенным FK и записываются
атомарно; поддельная запись без реестра отклоняется. Записи неизменяемы.

API:

- GET `/v1/service-orders/market/finance?propertyId=...&cursor=...`.
- POST `/v1/service-orders/market/:id/credits`, UUID Idempotency-Key:
  `{"expectedRevision":1,"amountMinor":"10000","reason":"Корректировка за недовоз"}`.

Сумма — строка в минимальных единицах. UI принимает обычную сумму валюты и
преобразует её через bigint. Cookie BFF фиксирует объект; клиент не задаёт scope.
Бухгалтерский интерфейс добавлен только для роли accountant с finance.manage.

## Блок 12: физический возврат

Склад принимает товар по завершённому заказу: позиция, фактическое количество,
причина и подтверждение получения. Товар попадает в карантин, доступный остаток
не растёт. Количество принятых возвратов, включая утилизированные, не может
превысить фактически выданное по заказу. Пилот ограничен 20 приёмками на заказ;
все ожидающие проверки остаются видны.

После осмотра сотрудник либо подтверждает утилизацию, либо отмечает три проверки:
заводская упаковка цела, срок годности проверен, качество и условия хранения
проверены. Только тогда появляется одно положительное складское движение
`return`. Оно увеличивает физический/доступный остаток и ревизию склада,
инвалидируя старые результаты инвентаризации. Утилизация ничего в продажу
не возвращает. Повторная обработка закрытого возврата запрещена.

Приёмка/инспекция требуют `stock.manage`; бухгалтер и гость не могут выполнять
складские команды. Корректировка фолио не создаёт складского движения, а возврат
товара не уменьшает начисление автоматически. Гость видит отдельные статусы.

Миграции 0091–0093: `market_returns` со scoped FK/RLS, связь с уникальным
`supply_movements.market_return_id`, новый вид движения и проверка точного
совпадения количества/товара/объекта/инспекции. Старые миграции не менялись.
Существующие триггеры баланса, разрешений и ревизии склада продолжают работать.

Существующий POST `/v1/service-orders/market/:id/actions`:

| action | Поля кроме expectedRevision |
|---|---|
| receive_return | serviceId, quantity (1–50), note |
| restock_return | returnId, note, checklist: sealed/expiry/quality = true |
| discard_return | returnId, note |

Каждая команда имеет UUID Idempotency-Key, revision, audit/outbox. Блокировки
брони и заказа сериализуют возврат с корректировкой; складские блокировки
совместимы с выдачами и инвентаризацией. Ошибка откатывает всю операцию.

## Запуск и ручная приёмка

Применить миграции штатным migrator с локальными флагами из
[блока 7](CANVA_140_BLOCK_7_MARKET_CORE_WEB.md). Постоянную views_local не сбрасывать.
Автономная проверка использует только одноразовую синтетическую базу:

```sh
npm run build
npm --prefix apps/api run build
VIEWS_GUEST_EMAIL_HTTP_PROOF=true VIEWS_GUEST_EMAIL_BROWSER_PROOF=true node scripts/cloud-core-tests.cjs
```

Проверить вручную:

- Бухгалтер: точная сумма, причина для гостя, повтор после потери ответа, закрытое фолио.
- Склад: карантин не доступен для продажи; три проверки обязательны для возврата в остаток.
- Утилизация подтверждает фактическое действие сотрудника, не автоматическое уничтожение.
- RU/UZ/EN, Light/Dark, узкий экран, длинные причины, работа без сети.
- Чек-лист не заменяет санитарные правила и прослеживаемость партий: проверить с ответственным.

Ограничения: нет фото и партий/серий, приёмка только после подтверждённого
получения и начисления. Неполученные/недостающие товары до начисления остаются
обращением; частичное начисление ещё не реализовано. Возврат денег через провайдера
не включён. Публичный веб/APK остаётся 0.14.0-preview. Все 140 экранов не завершены.

## Проверено на исходниках поверх 46896f5

- Web: typecheck/build, 330 тестов в 63 файлах — успешно.
- API: typecheck/build, 533 теста в 90 файлах на одноразовом PostgreSQL 16 — успешно;
  миграции до 0093 включительно. Профильный повтор: 56 тестов в 7 файлах.
- Браузер V Market с настоящим Core/PostgreSQL: карантин не меняет остаток,
  инспекция возвращает одну единицу без корректировки счёта; бухгалтерская
  корректировка после потери ответа повторяется с тем же ключом, даёт одну запись
  и не меняет склад. Итог счёта и видимость гостю проверены запросом к БД и UI.
- RU/UZ/EN на узком экране: гость, склад, бухгалтер без горизонтального переполнения.
- Network gate: 180 файлов, нарушений нет; mail acceptance: 15 тестов успешно.
- Первый полный браузерный прогон выявил гонку в проверке offline отмены брони:
  проверка читала disabled до обработки события React. Тест теперь ожидает
  disabled, затем проверяет его; повтор сценария прошёл. Логика отмены не менялась.

Доказательства относятся к синтетическому локальному процессу. Фото/PDF-приёмка
всех экранов, реальные провайдеры и публикация этим прогоном не подтверждаются.

Повтор всей цепочки HTTP/BFF/browser завершился с exit 0: поездки/привязка,
