# Canva 140 — изменение корзины до сборки

Базис: `42564b0`. Расширены SG-MK-002, SG-MK-004 и SD-MK-002 из переданного PDF.
Это изменение состава самим гостем, а не предложение замены от склада.
Публичный веб/APK 0.14.0-preview этим блоком не обновляется.

## Правила и интерфейс

Только владелец брони может изменить заказ на стадии `reserved`, до начала
сборки. В карточке есть «Изменить состав заказа»: гость выбирает весь новый
состав по актуальным ценам, видит исходную и новую суммы и заново даёт согласие.
Корзина начинает редактирование пустой: нельзя незаметно принять новый товар
или новую цену. Доступное количество включает собственный резерв выбранного
заказа; окончательная проверка всегда выполняется Core.

До подтверждения исходный заказ остаётся действующим. При успехе он отменяется,
создаётся новый заказ со своим снимком состава и цены. Обе карточки показывают
идентификатор связанного заказа. Склад начинает сборку нового заказа
сначала, с обычным чек-листом. Другие заказы гостя не затрагиваются.

Изменение после начала сборки, выдачи или начисления запрещено. Нет предложения
замены со стороны склада, таймера ожидания согласия, частичного начисления,
доплаты провайдеру, денежного возврата или физического возврата на склад.
Это следующие самостоятельные сценарии. Компенсацию нельзя выдавать за
выполненную на основании отмены такого неоплаченного заказа.

## Миграция и API

`0085_market_guest_replacement.sql` добавляет `market_orders.replaces_order_id`,
составной FK в том же organization/property, запрет ссылки на себя и уникальность
последующего заказа. Прежние FORCE RLS и отсутствие прямой runtime-записи
сохраняются. Дополнительных прав персоналу нет; отдельные сиды не нужны.

Существующий гостевой POST `/v1/guest-identity/email/services/market/:id/actions`:

```json
{
  "action": "replace_order",
  "expectedRevision": 1,
  "expectedTotalMinor": "200",
  "lines": [{"serviceId": "<UUID из каталога>", "quantity": 2, "expectedRevision": 1}]
}
```

Действительная гостевая сессия, CSRF в BFF и UUID Idempotency-Key обязательны.
Идентификаторы организации/брони клиент передать не может. Проверяется владение
бронью до и после блокировки. Суммы остаются строками bigint minor units.

Core блокирует бронь, старый заказ, текущие записи каталога и объединение старых
и новых складских товаров в порядке UUID. В одной транзакции освобождает старый
резерв и вызывает существующий движок оформления корзины. Нехватка товара,
изменённая цена/ревизия, неактивный товар или недопустимое проживание откатывают
всю замену. Исходные снимок цены, складской физический остаток и фолио не меняются.

Повтор того же ключа возвращает один и тот же новый заказ; другие данные с тем же
ключом отклоняются. Гонка со сборкой допускает только одну команду с ожидаемой
ревизией. События создания и замены фиксируются через общий audit/outbox.

## Запуск

Применить миграции штатным migrator при локальных флагах из
[блока 7](CANVA_140_BLOCK_7_MARKET_CORE_WEB.md). Не сбрасывать `views_local`.
Для автономной проверки используются синтетические остатки в одноразовом PostgreSQL:

```sh
npm run build
npm --prefix apps/api run build
VIEWS_GUEST_EMAIL_HTTP_PROOF=true VIEWS_GUEST_EMAIL_BROWSER_PROOF=true node scripts/cloud-core-tests.cjs
```

## Что проверить вручную

- Новый полный состав, исходная/новая суммы, повторное согласие и отмена редактирования.
- После начала сборки обновлённая карточка больше не предлагает изменение.
- Связь отменённого и нового заказов в гостевом и складском интерфейсах.
- RU/UZ/EN, Light/Dark, узкий экран и длинные названия товаров.
- Сбой сети: повтор той же команды, без создания третьего заказа.
- Работа с недовозом после выдачи идёт через обращение из блока 8; это не возврат денег.

Риски: локальные изменения не заменяют публикацию, приёмку PDF и проверку на
физическом Android. Сроки претензий/фискальные правила проверить с бухгалтером
и юристом перед боевым использованием. Вопросов для продолжения блока нет.
