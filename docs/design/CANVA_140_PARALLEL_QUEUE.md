## Пакеты и порядок объединения

Пакет — область ответственности, **не один большой diff**. Каждый разбивается на сценарии около 300 строк с 3–7 критериями, критичными тестами и независимой приёмкой. Общие миграции/маршруты/registry изменяет один интегратор; отдельные разработчики не редактируют их одновременно.
P0: G (точная навигация заказа), M (освобождение резерва партий), контроль исходников/визуальных доказательств — независимы по файлам. Далее P1: W/L/C/Q/F (персонал/прачечная/консьерж/общая очередь/финансы), N (коммуникации). После scoped-основы P: T/R/E/B (трансфер/прокат/туры/билеты). H (хост), A (конструктор) и S (SLA) имеют общие версионируемые контракты и идут отдельными последовательными срезами.
Все таблицы ниже задают зависимость до рабочего сценария; подготовить контракт/тест в sandbox можно раньше. Отсутствие договора блокирует реальную продажу, а не проектирование. Реальные цены/SLA/налоги/провайдеры из макетов не утверждены: **проверить**.

## Что можно делать параллельно сейчас

1. G: точный переход из общего списка в уже существующий scoped-заказ; отдельные адаптеры четырёх услуг, тест позднего ответа/смены поездки и browser proof. Схема/права не расширяются.
2. M: все пути освобождения lot-reserve (отмена → замена → выдача) отдельными транзакционными срезами; команда остаётся закрыта до завершения инвариантов и API/UI. Не включать runtime только ради экрана.
3. W/L/C: независимая приёмка одного существующего сценария за раз по reference WebP; редактор конкретной feature-папки, reviewer и browser agent разделены. Нельзя автоматически объявить все partial готовыми.
4. P: сначала локальная модель партнёрского scope/invitation/очереди, deny/cross-tenant тесты; не предоставлять партнёру staff-права. Это предпосылка новых рабочих транспортных/курьерских экранов.
5. S/A/N: сначала версии правил и read-only контракт одной матрицы/шаблона; публикация, таймеры и отправка отдельными срезами. Не параллелить миграции до выделения единственного владельца.

## Что проверить перед объединением

- Каждый срез: критерии → red критичного теста → реализация → зелёные профильные тесты; web/API typecheck/build, обязательные network/mail gates; итоговая общая browser chain на объединённом коде.
- Для каждого затронутого ID приложить источник и доказательство обеих тем; проверить ошибки/пустое/нет сети/отзыв доступа. Только после этого обновлять registry; скриншот макета не доказательство runtime.
- Миграции неизменяемы после применения; только disposable PostgreSQL, без реальных платежей/писем/документов/секретов. PR/код объединяются в feature-ветку; выпуск публичного веб/APK требует отдельной проверки сборки.
- Для новых внешних направлений: подтвердить продавца, поддержку, условия отмены/возвратов и договор; юридические/внешние факты помечены «проверить».
- Блокирующих вопросов для первой параллельной волны нет. Для повторного экспорта/текстовой приёмки потребуется исходный 140-screen PDF, но работу по сохранённым макетам это не останавливает.
