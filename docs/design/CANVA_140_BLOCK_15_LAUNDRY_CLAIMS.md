## Процесс

После согласования описи, в обработке, при возврате или после получения гость
выбирает существующую бирку и причину: потеря, повреждение, качество обработки.
Описание — 3–500 символов. Создаётся состояние open. Сотрудник с
reservation.manage своего объекта отвечает после проверки описи: answered.
Ответ не закрывает претензию. Гость может сообщить, что проблема осталась
(report_claim → open), либо явно закрыть/отозвать её (resolve_claim → resolved).
Гость вправе отозвать open до ответа; интерфейс объясняет смысл подтверждения.

Пока претензия open/answered, confirm_receipt отклоняется сервером. Закрытие
претензии не начисляет деньги: получение и начисление подтверждаются отдельным
действием гостя. Претензия после закрытия прачечной не сторнирует прошлое начисление.
Ни один новый переход не отправляет деньги и не обещает компенсацию.

История содержит действия, время и текст; не перезаписывается при повторном
обращении. Лимит — восемь записей обращения/ответа/предыдущих закрытий, затем
остаётся финальное закрытие (максимум девять). Интерфейс предлагает обратиться
на ресепшен. Это ограничение локального пилота, а не юридический срок претензии.
Автоматического срока отказа в претензии нет; проверить правила с юристом.

## Данные, API и безопасность

Миграция 0101 добавляет claim в laundry_intakes и расширяет действующий процесс.
Сохраняются scoped FK, FORCE RLS и отсутствие прямой runtime-записи из блока 5.
Авторизация повторно проверяется после блокировок и до возврата результата
идемпотентного повтора. Гость должен владеть бронью; сотрудник — иметь права
объекта. Изменения требуют UUID Idempotency-Key и expectedRevision.
Конкурирующие записи сериализуются. Audit/outbox пишутся в той же транзакции.

Используются существующие маршруты POST:
`/v1/guest-identity/email/services/laundry/:id/actions` и
`/v1/service-orders/laundry/:id/actions`.

- report_claim: expectedRevision, tag, kind, note (только гость).
- answer_claim: expectedRevision, note (только сотрудник).
- resolve_claim: expectedRevision (только гость).

Cookie BFF сохраняет CSRF и белый список полей. В истории гостя нет внутренних
ID сотрудников. Списки прачечной сокращены до двух заявок на страницу с cursor,
чтобы описи и история не раздували ответы шлюза. Каталог услуг не изменён.
Текст претензий хранится в Core и командном журнале; срок хранения и удаление
персональных данных требуют отдельной политики до публичного запуска.

## Запуск и проверки вручную

Применить миграции до 0101 существующим мигратором после проверки checksum.
Не сбрасывать и не заполнять синтетическими данными пользовательскую views_local.
Локальный запуск — как в блоке 7: NODE_ENV=test, VIEWS_LOCAL_REHEARSAL=true,
VIEWS_SERVICE_ORDER_PILOT_ENABLED=true и действующие флаги аутентификации.

```sh
npm run build
npm --prefix apps/api run build
npm test
VIEWS_GUEST_EMAIL_HTTP_PROOF=true VIEWS_GUEST_EMAIL_BROWSER_PROOF=true node scripts/cloud-core-tests.cjs
node scripts/core-network-primitive-gate.mjs
node --test scripts/staff-mail.acceptance.cjs
```

- Сверить бирку, причину и историю в интерфейсах гостя/сотрудника.
- Проверить запрет начисления и после создания претензии, и после ответа.
- Отдельно подтвердить закрытие претензии и получение вещей: одно начисление.
- Проверить повтор, гонку, чужую бронь, потерю сети и пагинацию сотрудника.
- Проверить повторную претензию после получения: прежняя сумма не меняется.
- Пройти клавиатурой, проверить RU/UZ/EN и Light/Dark на телефоне.
- С управляющим и юристом проверить ответственность за вещи, порядок оценки
  ущерба, сроки ответа, компенсации и работу с фото-доказательствами.

Внешние прачечные, фото, возвраты провайдера и полная приёмка PDF не включены.
Публичные web/APK остаются 0.14.0-preview и не содержат этот локальный блок.
